Optimization and Conversion of ONNX Models.py代码实现了一个**完整的 PyTorch 模型转 ONNX、图级精简、ONNX Runtime 会话配置、多 Batch 精度对齐与推理延迟基准测试**的端到端脚本。

下面按**总体架构、核心模块逐段解析、关键工程细节**三部分进行详细说明。

---

### 一、 总体执行链路

脚本从 `main()` 入口按顺序推进 4 个阶段，构成“导出 → 精简 → 加载执行 → 校验测速”的闭环：

1. **模型定义与实例化**：构建 `SimpleModel`（`Linear -> LayerNorm -> GELU -> Linear`），相比纯 `Linear + ReLU` 多了归一化和平滑激活，能更真实地体现算子图结构与数值精度检查的价值。
2. **导出与图合法性校验（`export_to_onnx`）**：将 PyTorch 计算图导出为 `simple_model.onnx`，并调用 `onnx.checker.check_model` 验证拓扑与类型规范。
3. **离线图精简（`simplify_onnx_model`）**：尝试使用 `onnxslim` 折叠常量、清理冗余节点并保存为 `optimized_model.onnx`；若未安装 `onnxslim`，则降级复制原图，把优化交给后续的 ONNX Runtime。
4. **会话构建、精度验证与基准测试（`create_session` + `verify_and_benchmark`）**：创建开启全量图优化的 `InferenceSession`，针对不同 `batch_size` 对比 PyTorch 与 ONNX Runtime 输出误差，并在预热后统计平均推理延迟。

### 二、 核心模块逐段解析

#### 1. `SimpleModel`：示例网络结构

```python
class SimpleModel(nn.Module):
    def __init__(self, in_features: int = 10, hidden_features: int = 20, out_features: int = 2):
        super().__init__()
        self.fc1 = nn.Linear(in_features, hidden_features)
        self.norm = nn.LayerNorm(hidden_features)
        self.act = nn.GELU()
        self.fc2 = nn.Linear(hidden_features, out_features)

```

* **结构特点**：包含两层全连接、一层 `LayerNorm` 和一层 `GELU`。
* **作用**：`LayerNorm` 与 `GELU` 在导出和运行时都比简单 `ReLU` 更容易暴露算子分解、归约维度或数值误差问题，也更适合观察图优化效果。

#### 2. `export_to_onnx`：模型导出与版本兼容

* **`model.eval()`**：将模块切至推理状态，防止训练态逻辑影响计算图。
* **`dynamo=True` 优先 + `TypeError` 回退**：
* 较新 PyTorch 版本支持 `dynamo=True`（基于 `torch.export` 的新导出路径），传入 `(dummy_input,)` 作为示例输入元组。
* 若运行在不支持 `dynamo` 参数的旧版本 PyTorch 中，捕获 `TypeError` 后回退到传统 `torch.onnx.export` 签名。


* **动态维度与 Opset**：
* `opset_version=17` 提供较完善的算子语义支持。
* `dynamic_axes={"input": {0: "batch_size"}, "output": {0: "batch_size"}}` 将输入、输出的第 `0` 维声明为可变 batch 维度，使后续 `batch_size` 为 `1、8、32` 时都能共用同一份 ONNX 模型推理。


* **`onnx.checker.check_model(onnx_model)`**：导出后立即做静态结构校验，及早发现非法图连接、类型不匹配或缺失属性。

#### 3. `simplify_onnx_model`：图精简与优雅降级

* **核心逻辑**：加载导出的 ONNX 模型，调用 `onnxslim.slim(model)` 进行常量折叠和冗余节点清理，再次通过 `onnx.checker.check_model` 校验后再保存为 `optimized_model.onnx`。
* **容错设计**：捕获 `ImportError` 后不会直接崩溃，而是保存副本并提示安装 `onnxslim`，同时依赖 ONNX Runtime 在加载会话时执行运行时图优化。

#### 4. `create_session`：推理会话与执行后端配置

* **图优化等级**：`options.graph_optimization_level = ort.GraphOptimizationLevel.ORT_ENABLE_ALL`，启用包括基础优化、扩展优化以及布局/融合优化在内的完整图优化策略。
* **线程与执行模式**：
* `intra_op_num_threads = intra_op_threads`（默认 `4`）：控制单个算子内部并行计算的线程数（如矩阵乘、归约等），对 CPU 推理延迟影响直接。
* `inter_op_num_threads = 1` 与 `ort.ExecutionMode.ORT_SEQUENTIAL`：算子间按顺序调度，减少多线程同步与上下文切换开销，对中小规模或串行结构模型通常更稳定。


* **Execution Provider（EP）选择**：动态查询 `ort.get_available_providers()`，若存在 `CUDAExecutionProvider` 则优先加入，最后兜底 `CPUExecutionProvider`。

#### 5. `verify_and_benchmark`：数值对齐与性能测量

* **多 Batch 动态测试**：遍历 `batch_sizes=(1, 8, 32)`，每次重新生成随机 `float32` 输入，同时验证动态 batch 推理与数值一致性。
* **精度断言**：
```python
max_abs_err = float(np.max(np.abs(pt_out - ort_out)))
is_close = np.allclose(pt_out, ort_out, rtol=1e-4, atol=1e-5)
assert is_close, f"batch_size={bs} 数值对齐失败，最大绝对误差: {max_abs_err}"

```


以 `rtol=1e-4, atol=1e-5` 作为浮点头对齐阈值，一旦偏差超标立即抛错并打印最大绝对误差。
* **Warmup 与高精度计时**：
* 先执行 `warmup=20` 次推理，让线程池、内存分配器或 GPU 上下文完成初始化。
* 再用 `time.perf_counter()` 统计 `runs=200` 次循环的总耗时，换算为单次平均延迟（`ms`）。

### 四、 实际使用时的关键细节

1. **计时口径与端到端开销**：`verify_and_benchmark` 统计的是 `session.run` 的推理耗时（不含 PyTorch 前向计算和 `np.random.randn` 数据生成时间）；若在 GPU 上测试，需注意主机与设备间的数据拷贝及异步调度特性。
2. **动态维度与 `dynamo=True**`：不同 PyTorch 版本下，`dynamic_axes` 在 `dynamo=True` 与传统导出器中的行为可能存在版本差异；若遇到动态维度导出报错，可先检查所用 PyTorch 与 `onnxscript` 版本是否匹配。
3. **小模型延迟的参考意义**：`SimpleModel` 计算量很小，测出的毫秒级延迟主要用于验证跑通流程与对比不同 `batch_size` 的扩展趋势，不能直接等同于大模型或复杂视觉/多模态模型的真实性能表现。
