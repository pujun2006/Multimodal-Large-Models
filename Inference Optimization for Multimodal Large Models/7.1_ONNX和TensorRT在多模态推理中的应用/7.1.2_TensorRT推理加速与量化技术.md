**TensorRT** 是 NVIDIA 面向自家 GPU 架构打造的**高性能深度学习推理优化器与运行时引擎**。如果说 ONNX 解决的是“跨框架的统一计算图表示”，那么 TensorRT 做的就是**针对特定型号 GPU（如 Ampere、Hopper、Blackwell 等）的底层硬件架构，把计算图编译成极致压榨 Tensor Core 与显存带宽的定制执行计划（Plan / Engine）**。

整个体系分为**构建期（Build Phase）的图编译优化**、**低比特量化技术**以及**运行期（Runtime Phase）的执行调度**三大支柱。

---

### 一、 核心推理加速机制（构建期编译优化）

深度学习推理的性能瓶颈往往不在算力上限，而在**频繁读写全局显存（HBM）带来的访存带宽瓶颈**以及**大量细碎 CUDA Kernel 的启动开销**。TensorRT 的图编译器重点围绕以下机制重写计算图：

#### 1. 纵向融合与横向融合（Layer & Tensor Fusion）
<img width="1651" height="556" alt="451f65f7-0576-413c-b7ba-004a327b3287" src="https://github.com/user-attachments/assets/2d85a875-bcb1-46d2-bedf-37b5421686b4" />

如上图 Inception 模块所示，TensorRT 通过两种维度大幅压缩计算图节点：

* **纵向融合（Vertical Fusion）**：将串行的 `Conv + Bias + ReLU` 合并为单个 **CBR** 算子（同理还有 `MatMul + Add + GELU`、LayerNorm、FlashAttention 等大算子融合）。中间特征图直接驻留在 GPU 的寄存器或共享内存（Shared Memory）中完成计算，彻底省去写回全局显存再读取的往返延迟。
* **横向融合（Horizontal Fusion）**：当多个并行分支对同一输入执行相同规格的操作（如上图中多个并行的 `1x1 conv + bias + relu`）时，TensorRT 会将它们合并为一个更宽的 `1x1 CBR` 算子一次执行，提高 SM（流式多处理器）的并行利用率。
* **消除冗余拼接（Concat Elimination）**：融合后相邻分支的输出可直接按偏移量写入后续算子的连续输出缓冲区，直接消去独立的 `Concat` 内存拷贝层。

#### 2. 内核自动调优（Kernel Auto-Tuning）

同一算子（如不同卷积核大小、步长、Batch Size 与数据排布）在 NVIDIA GPU 上存在数十种底层 CUDA/cuDNN/CUTLASS 实现方案。在构建 Engine 时，TensorRT 会针对**当前目标 GPU 的具体型号、SM 数量与缓存大小**，对候选 Kernel 进行真实计时基准测试（Benchmark），为每一层挑出实测延迟最低的实现方案并固化进 `.engine` 文件中（这也是 TensorRT Engine **强绑定特定 GPU 架构**的根本原因）。

#### 3. 动态形状优化配置文件（Optimization Profiles）

当输入存在动态维度（如动态 `batch_size` 或变长 `seq_len`）时，编译器无法在编译期知晓确切张量大小。TensorRT 通过 **Optimization Profile** 要求开发者指定三个关键形状锚点：`min`（最小形状）、`opt`（最常见最优形状）和 `max`（最大形状）：

* 编译器重点围绕 `opt` 形状选择最优 Kernel；
* 运行时只要输入落在 `[min, max]` 区间内即可直接复用已编译的 Kernel 与预分配显存池，无需重新编译。

#### 4. 静态显存池复用与张量内存优化

在图分析阶段，TensorRT 会追踪每个中间张量的生命周期（首次生成到最后一次被消费）。生命周期互不重叠的中间张量会被映射到同一块预分配的全局显存缓冲区（Activation Memory Pool）的不同偏移地址上，实现零运行时动态 `cudaMalloc` 开销与极低的峰值显存占用。

### 二、 量化技术体系（Precision & Quantization）

低比特量化（FP16、BF16、INT8、FP8、INT4/W4A16）通过**降低数据位宽**，同时带来两重收益：**显存占用与访存带宽减半/四分之一**，以及**触发 GPU Tensor Core 的高吞吐低精度矩阵乘指令**。

#### 1. 精度模式与硬件映射

* **FP16 / BF16（半精度）**：通常无需校准即可直接开启。BF16 保留了与 FP32 相同的 8 位指数位，动态范围极宽，几乎不会发生溢出，是现代大模型与 Transformer 推理的默认基线精度。
* **INT8（8 位整型）**：相比 FP32 带宽降至 $1/4$，计算吞吐翻倍。采用对称/非对称线性映射（$x_{real} = S \cdot (x_{int8} - Z)$），其中 $S$ 为缩放因子（Scale），$Z$ 为零点（Zero-Point，TensorRT 对权重和激活大量采用对称量化以省去零点计算开销）。
* **FP8（E4M3 / E5M2，Hopper 及更新架构原生支持）**：兼具低比特高吞吐与浮点数的非线性分布表示能力，对激活值存在离群点（Outliers）的 LLM 尤为友好。
* **权重量化（Weight-Only Quantization，如 W4A16 / W8A16）**：针对自回归生成（Decode 阶段）典型的访存受限（Memory-Bound）特征，仅将权重压缩至 INT4/INT8，推理加载进片上缓存后再反量化为 FP16 与激活相乘，大幅缓解权重读取带宽瓶颈。

#### 2. 两条核心 INT8 量化工作流：PTQ 与 QAT
<img width="685" height="418" alt="c24733a6-b754-4062-8b86-276832ab4687" src="https://github.com/user-attachments/assets/5a67934d-6252-45e8-af94-99daa226b628" />

如上图所示，TensorRT 针对 INT8 提供了两种主流落地路径：

* **训练后量化（PTQ，Post-Training Quantization — 左侧流程）**
1. **统计分布（Collect Statistics）**：向 TensorRT 传入一个小型且具有代表性的**校准数据集（Calibration Dataset，通常 100~500 批样本即可）**，在不修改权重的前提下跑前向传播，统计每一层激活张量的数值直方图。
2. **计算缩放因子（Compute Scales）**：校准器（Calibrator）根据直方图确定截断阈值 $T$，进而算出 $S = T / 127$。核心矛盾在于**截断误差与舍入误差的权衡**：
* **Entropy Calibrator（KL 散度校准，推荐默认）**：搜索最佳截断阈值 $T$，使量化后的离散分布与原始 FP32 分布之间的 **KL 散度（相对熵）最小**，在保留主体信息的同时过滤极端离群噪点。
* **MinMax Calibrator**：直接取校准集中的全局最大绝对值作为 $T$，实现简单但极易被单个离群值拉大 $S$，导致主分布精度严重退化。
* **Percentile Calibrator**：取 99.9% 或 99.99% 分位数作为截断边界，常用于存在长尾分布的视觉或序列模型。


3. **生成引擎**：将计算出的激活 Scale 与离线量化好的权重 Scale 写入量化缓存（Calibration Cache），构建 INT8 Engine。


* **量化感知训练与显式量化（QAT & Explicit Quantization / QDQ — 右侧流程）**
* 当 PTQ 精度掉点无法接受时，在训练/微调框架（如 PyTorch `pytorch-quantization` 或 NVIDIA ModelOpt）中插入**伪量化节点（FakeQuant）**，模拟前向传播中的舍入与截断误差，并通过直通估计器（STE）反向传播更新权重，使模型主动适应低比特噪声。
* 导出 ONNX 时，这些节点会被规范表示为标准的 **`QuantizeLinear`（Q）与 `DequantizeLinear`（DQ）节点对**。TensorRT 解析到 QDQ 图后，会自动将其折叠进前后算子并编译为原生低精度融合 Kernel（即**显式量化模式**），无需再在 TensorRT 内部重新跑校准。



#### 3. 混合精度回退（Mixed-Precision Fallback）

并非所有层都适合强行压到 INT8。在构建阶段，如果某层在 INT8 下的 Kernel 实际耗时反而高于 FP16（例如小张量维度无法填满 Tensor Core），或开发者通过精度逐层诊断工具（如 Polygraphy）发现某些敏感层（如首尾层、LayerNorm、Softmax 或回归预测头）误差过大，TensorRT 允许通过精度约束（Precision Constraints）将这些层**回退保留为 FP16 或 FP32**，在精度与延迟之间取得最优平衡。

### 三、 端到端工程落地流程与运行时调优

在实际部署（ONNX → TensorRT Engine）中，标准工程流水线如下：

1. **前置图清理**：先对导出的 ONNX 模型运行图精简（如 `onnxslim` / Polygraphy surgeon），消除冗余 `Shape`/`Gather`/`Cast` 链条，避免打断 TensorRT 的模式匹配融合规则。
2. **构建序列化引擎（`trtexec` 或 Python/C++ Builder API）**：
* 固定工作空间上限（Memory Pool Limit），避免构建期搜索占用过多显存；
* 开启目标精度标志（如 `--fp16`、`--bf16`、`--int8` 或 `--fp8`）；
* 配置多档 `min/opt/max` Profile 并序列化保存 `.engine` / `.plan` 文件，**切勿在生产服务启动时实时编译模型**（编译复杂模型耗时可能高达数分钟）。


3. **运行时（Runtime）极致调度**：
* **多上下文并发（Multiple ExecutionContexts）**：同一个 `ICudaEngine` 持有只读权重，可创建多个轻量级 `IExecutionContext` 绑定到不同的 **CUDA Stream** 上并发处理多路请求。
* **CUDA Graph 捕获与重放**：对于输入形状固定的推理负载（如 LLM Decode 阶段每步固定 `seq_len=1`），使用 CUDA Graph 将整条推理流水线的数百次 Kernel Launch 录制为单张静态执行图，将 CPU 侧发射开销（Launch Overhead）降至微秒级。
* **异步流水线重叠（Overlap）**：利用锁页内存（Pinned Memory）与多 CUDA Stream，将当前批次的 `H2D`（主机到设备数据拷贝）、上一批次的 `Compute`（GPU 计算）与更早批次的 `D2H`（结果回传）在时间轴上重叠隐藏。
