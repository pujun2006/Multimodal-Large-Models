Dynamic Batch Inference.py代码展示了一套完整的**基于 TensorRT 10/11 与 PyCUDA 的动态 Batch（动态批次）推理流水线**：涵盖 ONNX 模型自动生成、带 `OptimizationProfile` 的引擎构建与序列化、显存动态绑定与异步执行，以及多批次延迟与吞吐量基准测试。

整体结构清晰、现代（使用了 TensorRT 10+ 推荐的张量名接口 `get_tensor_name`、`set_tensor_address`、`execute_async_v3`），非常适合作为学习或验证动态维度推理的参考模板。下面按模块拆解核心原理、关键细节与可优化点。

---

### 一、 核心架构与工作流概览

整个脚本分为四个协作阶段：

1. **ONNX 准备（`create_sample_onnx_if_missing`）**：若本地没有模型，则构造一个两层 MLP（`Gemm -> Relu -> Gemm`），显式将输入输出的第一维设为动态符号 `"batch_size"`。
2. **引擎构建（`build_dynamic_engine`）**：解析 ONNX，配置显存池与可选 FP16，通过 `OptimizationProfile` 声明 `min / opt / max` 三档动态形状，最后构建并序列化保存 `.engine` 文件。
3. **推理执行器（`PyCudaTrtDynamicRunner`）**：反序列化 `.engine`，创建 `ExecutionContext` 与 CUDA `Stream`；每次推理按当前输入形状动态推断输出维度、分配/释放显存，并通过异步拷贝与 `execute_async_v3` 完成计算。
4. **基准测试（`main`）**：针对 `batch_size` 为 `1`、`8`、`32` 的输入分别做预热（5 次）与正式计时（50 次），统计平均耗时和每秒样本吞吐量（`samples/s`）。

---

### 二、 逐模块详细解析

#### 1. 动态 Batch 的 ONNX 模型构造

* 使用 `helper.make_tensor_value_info("input", TensorProto.FLOAT, ["batch_size", in_features])` 将维度 `0` 设为字符串 `"batch_size"`（在 ONNX 中代表动态维度，而非固定整数）。
* 权重与偏置通过 `helper.make_tensor(..., raw=True)` 转为字节流放入 `initializer`，网络结构为典型的全连接层 + ReLU 激活。
* `onnx.checker.check_model(model)` 会在保存前校验计算图合法性。

#### 2. 引擎构建与 `OptimizationProfile`

* **显存池配置**：`config.set_memory_pool_limit(trt.MemoryPoolType.WORKSPACE, workspace_mb * (1 << 20))` 指定构建阶段允许使用的工作空间上限（字节）。
* **动态形状档位（Profile）**：
* `min=(min_batch, in_features)`：引擎支持的最小输入形状；运行时若小于此值会报错。
* `opt=(opt_batch, in_features)`：TensorRT 内核自动调优与算子选择的**最优参考形状**，通常设为线上最常见的 batch 大小。
* `max=(max_batch, in_features)`：引擎支持的最大输入形状，决定构建/运行时所需的最大显存上限。


* **序列化**：`builder.build_serialized_network(network, config)` 生成序列化字节流并写入磁盘，避免每次启动重复耗时编译。

#### 3. 现代 TensorRT（10/11）推理接口适配

相比早期依赖绑定索引（binding index）和 `execute_async_v2` 的写法，这段代码采用了更规范的新版张量接口：

* **枚举输入/输出张量**：遍历 `0 .. engine.num_io_tensors - 1`，通过 `get_tensor_name` 与 `get_tensor_mode`（`INPUT` / `OUTPUT`）分离输入输出名。
* **动态形状设置与推导**：
1. `in_contig = np.ascontiguousarray(input_data, dtype=np.float32)` 保证主机端内存连续，防止异步拷贝出现 stride 问题。
2. `self.context.set_input_shape(in_name, in_contig.shape)` 将本次实际 batch 大小告知执行上下文。
3. `self.context.get_tensor_shape(out_name)` 读取推导后的输出形状，并检查是否仍有 `< 0` 的未解析维度。


* **地址绑定与异步执行**：
* `set_tensor_address(name, int(d_ptr))` 将设备端指针绑定到对应张量。
* 在同一个 `cuda.Stream` 上依次提交 `memcpy_htod_async` → `execute_async_v3(self.stream.handle)` → `memcpy_dtoh_async`，最后调用 `self.stream.synchronize()` 等待整条流水线完成。



#### 4. 计时模式与基准统计

* `infer` 中提供了两种计时方式：
* `measure_kernel_ms=True`：使用 `cuda.Event` 记录在 `self.stream` 上的起止时间，更贴近 GPU 侧事件间隔测量（注意若 `end_evt` 在 `execute_async_v3` 后、且 `memcpy_dtoh_async` 前记录，不包含回传拷贝；当前代码中 `end_evt.record` 在 `execute_async_v3` 之后、`memcpy_dtoh_async` 之前，并在 `synchronize()` 后调用 `time_since`）。
* `measure_kernel_ms=False`（`main` 中当前使用）：使用 `time.perf_counter()` 包裹 `execute_async_v3` + `memcpy_dtoh_async` + `stream.synchronize()`，反映的是**包含 GPU 执行、结果回传及主机同步在内的单次推理端到端耗时**（注意 `memcpy_htod_async` 放在了计时之外）。


* 吞吐量计算公式为：`batch_size / (avg_ms / 1000.0)`，单位为 `samples/s`。

### 四、 潜在细节与工程优化建议

1. **每次 `infer` 都 `mem_alloc` / `free` 会有额外开销**
* 当前每次调用 `infer` 都会分配并释放 `d_input`、`d_output`。对于高频推理或大图模型，频繁申请释放显存会引入驱动开销并增加显存碎片。
* **优化方向**：可在类内缓存显存缓冲区（当所需字节数不超过已分配容量时复用，仅在 `batch_size` 超过当前容量时扩容），或按 `max_batch` 预分配后按切片绑定地址。


2. **`in_features` 与 ONNX 输入维度的关联**
* `build_dynamic_engine` 接收了 `in_features` 参数用于 `profile.set_shape`，但未校验它是否与 ONNX 模型实际输入特征数一致；若传入不一致会导致构建或运行时报错。建议从 `network.get_input(0).shape[1]` 读取或做断言校验。


3. **Host 端页锁定内存（Pinned Memory）**
* 使用 `np.empty` / `np.random.randn` 分配的是普通可分页内存，异步拷贝（`memcpy_*_async`）在底层可能需要额外 staging 缓冲；对延迟敏感的场景可改用 `cuda.pagelocked_empty` 分配锁页内存。


4. **`BFLOAT16` 映射细节**
* `_trt_dtype_to_np` 中遇到 `BFLOAT16` 时返回了 `np.float32`，这在通用回退上比较安全，但若实际引擎输出为其他低精度类型，需确保下游消费者能正确解释数值范围。
