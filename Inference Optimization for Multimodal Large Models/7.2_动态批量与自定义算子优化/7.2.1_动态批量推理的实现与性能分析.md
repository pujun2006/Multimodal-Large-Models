在 TensorRT 中实现动态批量推理（Dynamic Batch Inference），核心是**在编译期通过 Optimization Profile 声明维度范围，在运行期通过 ExecutionContext 动态绑定 Shape 与显存地址**。结合上述代码，具体实现机制与性能特征分析如下：

---

### 一、 动态批量推理的实现机制（四阶段闭环）

动态 Batch 并非简单地向模型传入任意尺寸张量，而是跨越模型导出、引擎编译、运行期调度三个阶段的系统工程：

1. **图表示阶段（ONNX 符号维度声明）**
* 在 `export_to_onnx` 中，通过 `dynamic_axes={"input": {0: "batch_size"}, "output": {0: "batch_size"}}` 将第 0 维标记为符号维度（`-1` 或 `batch_size`），避免导出工具将 `batch=1` 固化为常量算子（Constant Folding 阶段若误把 batch 折叠为静态常数，后续将无法动态调整）。


2. **编译期优化阶段（Optimization Profile 三档约束）**
* 在 `build_engine_trt11` 中，TensorRT 11 要求为每一个动态输入张量配置 `IOptimizationProfile`，明确指定 `min`、`opt`、`max` 三组维度：
* **`min` 与 `max**`：定义合法输入边界及显存激活值（Activation Memory）的最大分配上限；运行时超出该范围会直接报错。
* **`opt`（核心调优锚点）**：TensorRT 的 Auto-Tuner 在构建期会基于 `opt` 形状对各类 CUDA Kernel（Tactic）进行真实计时基准测试，选出最快的算子融合方案与分块策略（Tiling）。




3. **运行期形状推导与地址绑定（`Trt11Runner.infer`）**
* **Shape 注入与传播**：每次推理前调用 `context.set_input_shape(in_name, in_contig.shape)`。TensorRT 的 Shape Machine 会立即沿计算图前向推导出所有中间张量及输出张量的精确尺寸，随后通过 `context.get_tensor_shape(out_name)` 即可获取当前 Batch 对应的输出维度。
* **零拷贝指针绑定**：利用 `set_tensor_address(name, int(tensor.data_ptr()))` 将 PyTorch 分配的显存地址直接绑定给执行上下文，最后通过 `execute_async_v3(stream.cuda_stream)` 在指定非默认 CUDA Stream 上异步发射内核（避免默认流引发隐式的 `cudaDeviceSynchronize()` 性能损耗）。


4. **多并发隔离（多 `ExecutionContext` 模式）**
* 单个 `ICudaEngine` 可派生多个独立的 `IExecutionContext` 实例。高并发服务中，通常为每个工作线程分配独立的 `ExecutionContext` + `cudaStream`，互不干扰地处理不同 Batch Size 的请求。

### 二、 动态批量推理的性能分析

#### 1. 延迟（Latency）与吞吐量（Throughput）的非线性权衡

对于 GPU 推理，单次调用的端到端时间可拆解为固定开销与计算/访存开销：

$$T_{\text{total}}(B) = T_{\text{host\_overhead}} + T_{\text{H2D/D2H}}(B) + T_{\text{compute}}(B)$$

其中系统吞吐量（Samples/sec）为：

$$\text{Throughput}(B) = \frac{B}{T_{\text{total}}(B)}$$

* **小 Batch 区间（如 `batch=1` 至 `8`）—— 带宽与调度受限（Memory/Enqueue Bound）**：
* 小模型（如示例中的 2 层 MLP）或低 Batch 下，GPU 的流式多处理器（SM）远未打满。此时耗时的主要矛盾是 **Host 端内核发射开销（Enqueue Time）、Python/C++ 胶水层调度以及权重从显存加载到寄存器的带宽延迟**。
* 增大 Batch 时，模型权重只需加载一次即可服务于整个 Batch 的样本（权重复用率提升），因此 **`batch=8` 的单次延迟往往仅比 `batch=1` 略微增加，而吞吐量却接近线性翻倍**。


* **大 Batch 区间（如 `batch=32` 及以上）—— 算力受限（Compute Bound）**：
* 当计算强度（Arithmetic Intensity）超过 GPU 的屋顶线模型（Roofline Model）拐点后，SM 算力单元达到饱和。继续增大 Batch，单次延迟 $T_{\text{total}}(B)$ 开始随 $B$ 近似线性增长，总体吞吐量趋于平台期。



#### 2. 当前代码在性能测量与执行上的 4 个关键瓶颈

代码中的 `Trt11Runner.infer` 和 `verify_and_benchmark` 适合功能验证，但在极致性能场景下存在明显的开销放大：

| 瓶颈环节 | 代码中的现状 | 对性能的具体影响与优化方向 |
| --- | --- | --- |
| **1. 逐次显存分配与 H2D/D2H 拷贝** | `infer()` 内部每次都执行 `torch.from_numpy(...).to("cuda")`、`torch.empty(...)` 和 `.cpu().numpy()` | 小模型下 PCIe 数据传输与 CUDA 显存分配器的耗时远超 Kernel 本身计算耗时（Enqueue/Transfer Bound）。生产环境应**预先按 `max_batch` 分配复用显存池**，并仅在纯 GPU 推理区间用 `cuda.Event` 统计纯计算延迟。 |
| **2. 频繁调用 `set_input_shape**` | 即使连续多次推理的 Batch 相同，每次 `infer()` 仍调用 `set_input_shape` 和 `set_tensor_address` | 当输入形状发生变化时，TensorRT 需要在主机端重新计算张量步幅与内核参数（Host Heuristics），带来额外的 CPU 调度开销。建议仅在 `shape != last_shape` 时触发 `set_input_shape`。 |
| **3. 无法直接使用单一 CUDA Graph** | 动态 Shape 每次可能改变张量维度与内核网格（Grid Size） | CUDA Graph 要求计算图拓扑与张量地址/维度完全固定。对于小模型，CPU 发射 Kernel 的开销占大头；生产中常针对高频离散档位（如 `B=1, 4, 8, 16`）分别捕获（Capture）多个 **CUDA Graph 实例**，运行时按实际 Batch 路由到对应 Graph 直接发射。 |
| **4. 精度模式仍为 FP32** | 未在 `builder_config` 中启用低精度（FP16 / BF16 / FP8 / INT8） | 默认 FP32 无法充分发挥现代 NVIDIA GPU 的 Tensor Core 吞吐优势。开启 FP16/FP8 通常可带来 1.5x～3x 的计算加速与显存带宽减半。 |

#### 3. 工程选型建议：如何设定 `min / opt / max`？

* **`opt` 必须贴近线上真实 P50/平均并发 Batch**：如果线上请求绝大多数集中在 `batch=4~8`，却将 `opt` 设为 `32`，TensorRT 会选择偏重高并行度的大分块 Kernel，导致小 Batch 下的 SM 利用率低下、延迟偏高。
* **跨度过大时拆分多个 Optimization Profile**：如果业务同时存在极低延迟的在线单条请求（`batch=1`）和离线大吞吐任务（`batch=64`），单一 Profile 很难兼顾两端最优。可在构建期向 `config` 添加两个 Profile（例如 Profile 0 专攻 `1~4`，Profile 1 专攻 `16~64`），运行时通过 `context.set_optimization_profile_async(profile_idx, stream)` 动态切换。
* **线上服务化组批（Opportunistic Batching）**：单靠 TensorRT 的动态 Shape 引擎只能“接收”可变 Batch，无法自动“攒批”。线上高并发服务通常需配合 **NVIDIA Triton Inference Server** 的 Dynamic Batcher，设置最大等待窗口（如 `max_queue_delay_microseconds = 2000`），以微小的排队延迟换取数倍的整体吞吐提升。
