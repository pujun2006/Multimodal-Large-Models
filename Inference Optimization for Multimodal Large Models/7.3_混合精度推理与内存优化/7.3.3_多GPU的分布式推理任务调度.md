多 GPU 分布式推理任务调度，核心目标是解决大模型推理在**吞吐量（Throughput）**、**延迟（TTFT 首字延迟与 TPOT/ITL 字间延迟）**、**显存容量（尤其是 KV Cache）**与**跨卡通信开销**之间的矛盾。

---

## 一、 推理负载特性与调度挑战

大模型推理天然分为两个计算特征迥异的阶段：

* **Prefill阶段（预填充）：** 并行处理整个输入 Prompt，计算密集型（Compute-bound），决定 **TTFT（Time To First Token）**，同时生成初始 KV Cache。
* **Decode阶段（解码）：** 自回归逐个生成 Token，每次前向计算读取历史 KV Cache，访存/带宽密集型（Memory-bandwidth-bound），决定 **TPOT / ITL（Time Per Output Token / Inter-Token Latency）**。

若将两者混在同一批次或同一组 GPU 上无差别调度，长 Prefill 会阻塞短 Decode 的字间延迟，而动态增长的 KV Cache 则极易引发显存碎片化与 **OOM（Out Of Memory）**。

---

## 二、 并行策略与执行拓扑

多 GPU 调度通常建立在特定的模型切分与部署拓扑之上，调度器需要感知通信带宽层级（NVLink / NVSwitch 高带宽域 vs. PCIe / InfiniBand / RoCE 跨节点网络）：

| 并行方式 | 切分维度 | 通信原语 | 适用场景与调度关注点 |
| --- | --- | --- | --- |
| **张量并行（TP）** | 单层权重矩阵按行/列切分 | AllReduce / ReduceScatter | 适合单机内高带宽互联（如 8×H100 NVLink）；切分过细跨节点通信开销急剧上升 |
| **流水线并行（PP）** | 模型层按阶段切分到不同 GPU/节点 | Send / Recv（点对点） | 适合跨节点部署超大模型；需配合微批次（Micro-batch）降低气泡（Pipeline Bubble） |
| **专家并行（EP）** | MoE 模型的不同专家分布在不同卡 | All-to-All | 路由倾斜会导致“热点专家”负载不均，需动态路由均衡或容量限制 |
| **数据并行（DP）** | 完整模型副本处理不同请求批次 | 几乎无同步通信 | 适合吞吐扩容，但需结合 **KV Cache 感知路由**避免重复计算前缀 |

## 三、 核心调度机制

### 1. 迭代级调度与批处理合并

传统静态批处理必须等整批请求全部完成才释放槽位，尾延迟高。现代推理引擎采用**迭代级调度（Iteration-level Scheduling）**：每生成一个 Token 就重新评估队列，新请求可立即加入、已完成请求立刻退出。

* **Chunked Prefill（分块预填充）：** 将超长 Prompt 拆分为固定大小的 Token 块，与当前活跃的 Decode 请求混合进同一前向迭代。这样既避免长上下文独占算力导致 Decode 卡顿，又能维持较高的 GPU 计算利用率。
* **抢占与换出（Preemption & Swap）：** 当显存紧张无法为活跃请求分配新 KV Cache 块时，调度器可将部分请求的 KV Cache 换出（Swap）到主机内存（CPU RAM）甚至磁盘，或直接重算（Recompute），释放显存后再择机恢复。

### 2. KV Cache 显存管理与前缀复用

KV Cache 占用随上下文长度与并发数线性增长，是制约并发上限的关键瓶颈：

* **分页管理（如 PagedAttention）：** 将逻辑上连续的 KV Cache 划分为固定大小的物理显存块（Block），通过块表映射，消除外部碎片并支持按需分配。
* **前缀缓存调度（Prefix Caching / APC）：** 多轮对话或共享 System Prompt / Few-shot 的请求具有相同前缀。调度器维护全局或节点级前缀树（Radix Tree / Block Hash），优先将请求路由到已缓存对应 KV 块的实例，跳过重复 Prefill 计算。

### 3. Prefill-Decode 分离（P/D Disaggregation）

由于 Prefill 和 Decode 对算力与显存带宽的诉求相反，越来越多的高并发系统将 GPU 划分为 **Prefill 实例池**与 **Decode 实例池**：

1. 路由/调度器根据当前两类实例池的队列长度、显存水位与前缀命中率分配节点。
2. Prefill 节点完成提示词计算后，通过高速网络（RDMA / NVLink）将生成的 KV Cache 传输给 Decode 节点。
3. Decode 节点专注执行低延迟自回归解码，避免长输入干扰输出流畅度。

## 四、 多副本与集群级路由调度

在多机多卡集群中，调度通常分为**全局/网关层路由**与**引擎/设备层本地调度**两级：

* **负载与缓存联合打分：** 传统轮询或最少连接数忽略了 KV Cache 局部性；现代调度器综合考虑待处理 Token 数、KV Cache 利用率、解码队列长度以及前缀缓存命中率进行打分路由。
* **SLO / 延迟感知调度：** 针对不同请求或业务等级设定 **TTFT** 与 **TPOT** 目标。当解码延迟逼近阈值时，限制新请求进入或调低 Chunked Prefill 预算，优先保障存量生成的平滑输出。
* **多租户与优先级队列：** 支持高优先级请求插队、按用户/业务配额限流，防止单一长上下文突发流量挤占全集群显存。

---

## 五、 常见调度痛点与调优方向

* **长上下文显存抖动：** 提前估算最大可能上下文长度或设置动态驱逐策略，避免突发长输出引发频繁 Swap 或 OOM。
* **批大小过小导致 Decode 带宽打不满：** 适度提升并发度或启用推测解码（Speculative Decoding），用草稿模型/并行验证提高单步计算访存比。
* **跨节点通信成为瓶颈：** 尽量让 TP 落在单机 NVLink 域内，跨机优先采用 PP、DP 或独立的 P/D 传输通道，减少高频集合通信跨越慢速网络。
